# 改错流程（F1.5）

OJ 的“诊断代码”按钮进入同一流程。`source: "oj"` 时按 [oj.md](oj.md) 输出结构化诊断，普通聊天按本文件末尾格式输出；两种入口都遵守下面的行号与证据规则。

## 触发
用户反馈 WA / TLE / RE / 编译错误，或贴回自己的代码 + 样例 / 评测结果，或说"哪错了 / 帮我改"。

默认在聊天中给出诊断、完整修正代码块和改动点；“帮我改 / 自检”不等于请求改写工作区文件或实际运行。只有用户明确指定保存、修改文件或运行测试时才执行相应操作；否则使用静态分析与手工反例，不调用编译器或 `sample_test.py`，不输出执行完成声明、文件清单或产物汇总。

## 处理流程（严格按序执行）

### 原代码行号与评测类型

- 以收到的原始代码第 1 行为起点，空行和注释也计行；只统一 CRLF/CR 换行，不格式化、不删空行。行号必须对应原代码中的逐行内容。应用提供的 sourceLines 可用于定位，修正代码中的行号不用于原代码标注。
- CE 是编译失败：优先解释编译器原文中的行、列与错误信息。编译器指出的报错行可能是前一行缺分号造成的连带错误，应区分报错位置与实际修改位置。没有编译输出时，可指出已证实的语法或类型错误，但不能捏造编译器消息。
- WA 是输出与要求不符：优先对照题意、范围、边界与状态转移。WA 说明提交通常已经编译成功，不因看到 WA 就硬找语法错误；TLE/RE/MLE 则结合对应资源或运行问题排查。
- 每个问题给出“原代码行或行段 + 对应原文 + 原因 + 修复方式 + 证据”。涉及声明和使用两处时分别引用；算法整体不成立或关键步骤缺失时，可以只定位相关循环/函数，或明确“无单独出错行”，不虚构精确行号。
- 自行构造的反例标为“构造反例”，同时给合法输入、正确输出与手工推演。官方失败输入不可用时说明未提供；推测用“可能”，静态证明用“可确定”。有符号溢出、越界等未定义行为不能给出必然的错误输出或崩溃结论。

### 排查与修正

1. 复用当前会话的题面、代码与反馈。若用户只说"错了"且上下文没有细节，一次性问缺失信息：评测结果是什么类型（WA/TLE/RE/CE）？哪组样例挂了？能贴一下代码吗？没有错误样例时也可依据完整题面与代码排查，但要说明诊断依据和验证范围。缺少决定算法与实现的题意、数据范围或输入输出格式时先补问；可指出代码中已证实的局部缺陷，但不猜测缺项给出整题修正版。
2. **重新对照数据范围算一遍复杂度预算**（同解题流程第 3 步）。在诊断末尾写时间量级、最大规模运算量和修正版的总空间：按实际同时存活的变量、数组、缓存与递归栈求和，而不是只算核心数据结构。例如两个 `long long[N]` 数组合计 `16*N` 字节；多测桶计数的主要循环量为 `Σn + T*(清空长度 L + 扫描长度 V)`，即使渐近式写作 `O(Σn + T*V)`，代入数值时也保留两项。例如 20 组各 1000 个元素，每组清 110 项、扫 100 项，主要循环量为 `20000 + 20*110 + 20*100 = 24200`，而非 22000。题面缺少限制时使用“题面未给时限/内存限制，以上为规模估算，需结合评测环境验证。”，不写“常规时限充裕”等无实测依据的结论。复杂度风险本身不能证明 WA 的具体原因。
3. 按【竞赛调试检查清单】逐项排查（按命中率排序）：
   1. **溢出**：中间结果或答案是否超 int（> 2^31）；注意 1e5 个 1e9 相加、k×mid 这类隐蔽乘加；
   2. **边界**：n=0 / n=1 / 全相同 / 空集 / 极值输入；
   3. **多测忘清空**：全局数组、vector、桶没在每组数据前重置；
   4. **数组开小 / 越界**：C++ 长度 L 的数组合法下标是 0..L-1；1-based 访问到 L 已越界，不是仅 L+1 才越界。检查差分、前缀和下标的 ±1、图建边 2×m、字符串结尾的 '\0'；修正时按最大实际下标开足并留 +10 余量；
   5. **读入输出格式**：多组数据、行尾空格、是否取模、是否需要 long long 读入（%lld / cin 默认）；
   6. **逻辑对照**：把用户代码的关键步骤与题意逐条对照，找出实现与思路的偏差。
4. 给出**诊断结论**：按上面的行号规则引用原代码，明确实现缺陷、语法问题或算法问题，并解释证据。区分静态证明、自己构造的反例与实际运行结果；未看到失败样例或运行记录时，不声称已复现该样例，也不把一种可能错因断言为唯一原因。
   没有找到可证缺陷时，到此交付当前结论和继续定位所需的失败信息，不强行进入“修正代码”步骤；OJ 返回空 `issues` 与空 `code`。单凭 WA 结果不能证明哪行错，风格或优化建议不充当 bug。
5. 输出**修正代码**：完整可编译（遵守 SKILL.md 全局规范；大规模输入启用 fast I/O，数组留 +10 余量），并在代码后用 1-3 行标注【改动点】。给出能证明缺陷的边界输入及预期行为；有符号溢出和数组越界是未定义行为，不承诺某个输入必然崩溃或产生固定错误值。用户明确要求运行时才使用工具验证，不把静态检查或样例通过说成 OJ 已 AC。
6. 提示用户重测；若修正后仍失败，升级为**换思路建议**——回到解题流程第 4 步重新选型。

改错也要交付符合规范的完整参考实现，不能仅在原代码中替换出错的一行就结束。输出前将诊断与最终代码对照：原数组首次非法下标必须与合法范围一致；存储字节按修正版数组长度求和，桶统计与清空分别计操作量。给定时限也不能把估算操作数直接换算为运行秒数或通过保证；若有实测，报告编译选项、环境和用例规模，未测的全数据性能仍待验证。修正版在 `main` 开头启用 `ios::sync_with_stdio(false); cin.tie(nullptr);`；已有数组按合法最大下标留足 +10 余量；多测按组重置。输出规范调整可与主因修正分开说明，不把原代码缺少 fast I/O 或余量误认作本次 WA 的已证实主因。

## 输出格式

```markdown
### 诊断
（先说明评测类型与主要结论）
（逐项列原代码行号、对应代码、原因与修复方式；算法整体问题不强行归于单行）
（构造反例的合法输入、正确输出与推演；未实际运行时注明静态分析）
（复杂度预算：时间 O(...)、最大规模下的运算量；总空间 O(...)、主要存储量；缺少限制时说明估算范围）

### 修正代码
（完整可编译 C++，含 fast I/O、数组 +10 余量与必要的多测重置）

### 改动点
- （1-3 行，指明改了哪里、为什么）

（末尾固定附：代码为参考实现，提交前请自行验证样例与边界。）
```

## 示例（错因定位口吻）

**用户输入**："这段第 3 个样例 WA 了"（贴代码：`int cnt = 0; for(...) cnt += a[i]/x; ... cin >> k;`，其中 n≤1e5、a_i≤1e9）

**诊断**：若 x 为正整数，cnt 累加 Σ⌊a_i/x⌋ 的上界可达 1e5 × 1e9 = 1e14，超过 32 位 int 的可表示范围，命中清单第 1 条（溢出）。例如 a=[1e9,1e9,1e9]、x=1 时，数学和为 3e9；C++ 有符号溢出属于未定义行为，不能保证具体错误值。尚未提供第 3 组样例内容，因此这里只证明类型缺陷，未确认它就是该样例的失败原因。

**改动点**：`int cnt` → `long long cnt`；k 同步改 `long long` 防混用比较。
